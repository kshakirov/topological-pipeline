# Ticket #3: Разработка параллельного контейнера вычислений на базе композиции ящиков

## 1. Назначение задачи
Спроектировать и реализовать новый инфраструктурный контейнер-оболочку для распараллеливания тяжелого потока данных (100+ запросов/сек) [📌]. Контейнер должен агрегировать внутри себя $N$ независимых вычислительных ящиков (`ComputeNode`/`Box`), скрывая параллельную физику вычислений за единым входным и выходным разъемом [📌].

## 2. Ключевые архитектурные вопросы к исследованию
В ходе реализации первого приближения необходимо проанализировать и решить следующие инженерные проблемы [📌]:
*   **Логика диспетчеризации (Такт IN)**: Каким образом входной функционал контейнера будет распределять входящие кванты данных между изолированными ящиками [📌]? Эффективен ли Round-Robin в условиях разного времени выполнения тяжелых задач?
*   **Проблема бутылочного горлышка на выхлопе (Такт OUT)**: Как минимизировать деградацию производительности, когда $N$ параллельных ящиков одновременно сдают результаты в единый аккумулирующий агрегат [📌]?
*   **Физика внутренней коммутации**: Как связать входной диспетчер с пулом ящиков (внутренние буферизированные шины/каналы) и как управлять их емкостью, чтобы избежать блокировки ввода [📌]?

## 3. Критерии приемки (Definition of Done)
- [ ] Описать структуру нового контейнера, инкапсулирующего пул из $N$ ящиков.
- [ ] Реализовать входной распределитель данных, работающий по алгоритму явной диспетчеризации (Round-Robin) [📌].
- [ ] Реализовать выходной сумматор потоков, собирающий результаты параллельной обработки в единый исходящий провод [📌].
- [ ] Проверить стабильность макета под нагрузкой: подтвердить параллельный хаотичный выхлоп воркеров по логам.
- [ ] Убедиться в отсутствии взаимных блокировок (Deadlocks) на стыках внутренних и внешних шин.

## 🎯 Задачи на следующий сеанс

### 1. Точный Round-Robin $O(1)$ в `LocalExternalChoice`
- [ ] **Убрать внутренний цикл `for`** в методе `WriteWithChoice()`.
- [ ] **Реализовать честную маршрутизацию:** 1 входящий Payload из `InChan` отправляется строго в один канал `BoxesChans[lsd.currentIndex]`.

- [ ] **Перевод на цикл генерации:** перевести `PrefixGenerator` с одиночного вызова `Start(b)` на непрерывную/пакетную генерацию серии префиксов (событий).
- [ ] **Закон Владения (Ownership):** гарантировать, что `PrefixGenerator` корректно закрывает свой выходной канал (`close(pg.OutChan)`) по окончании передачи.

- [ ] **Проверка штатного останова:** убедиться, что закрытие `InChan` штатно завершает цикл `for msg := range lsd.InChan` в Диспетчере и воркерах без дедлоков и зависания горутин.
- [ ] **Фиксация логов:** проверить корректность распределения нагрузки между воркерами `Node_1` и `Node_2`.

### @kshakirov — 2026-09-28T11:38:09Z

Промежуточный результат: Parallel Node теперь собирается с динамическим `Parallelism`, запускается одной точкой и распределяет работу атомарным round-robin. На трёх workers подтверждён цикл `1 → 2 → 3 → 1 → 2 → 3`; race detector замечаний не дал.

Следующий рубеж:

1. Реализовать потоковый ST decoder: `Magic → Length → Payload` с корректной сборкой кадра через произвольные TCP `Read`.
2. После полной сборки кадра передавать один `Payload []byte` одному worker; граница `Read` больше не участвует в маршрутизации.
3. Тот же framing использовать для связи NodeAgent с Elixir Coordinator, оставив трактовку payload верхнему уровню.
4. Зафиксировать минимальные управляющие сообщения `REGISTER`, `READY`, `CONNECT`, `RUN` и ответы на них.
5. После появления Coordinator убрать временные `Sleep`: сначала все входные listeners переходят в `READY`, затем Coordinator разрешает `CONNECT`, после успешных подключений — `RUN`.
6. Отдельно оформить штатный EOF-drain и аварийное завершение через context.

Data plane между узлами и control plane с Coordinator не смешиваются по смыслу, даже если используют общий ST framing.
